# 怎麼跟 AI agent 一起做出來的

*[Up to you](../README.zh-TW.md) 的開發是怎麼安排的：一個人、幾個 AI 寫程式的 agent session，以及夾在它們和 repo 之間的檢查。English：[harness.md](harness.md)。*

## 為什麼需要這一層

這個 repo 裡大部分的程式是 AI 寫程式的 agent 寫的。做什麼、看結果、做決定，是一個人。

agent 說「做完了」或「測試全過」，那只是它的說法。放著不管，它會自己給自己打分數、對話一長就忘記規則、讀到一段文字就被帶著走。所以重要的規則沒有交給 agent 的記憶，而是分成三種，這一頁會寫清楚每一條是哪一種：

- **程式碼強制**：有東西會拒絕這次 commit、這次推送或這次請求；
- **流程強制**：寫好的步驟，由人去跑，程式碼不會逼你做；
- **只是說明**：agent 開工時讀的文字指示。

## 角色

每個角色是一個 agent session，有自己的指示和自己負責的檔案。五個跑在開發機上，另外兩個在別的機器（一台有顯示卡，一個專門讀資料）。角色的指示檔本身不在公開的 repo 裡（私有）。

| 角色 | 做什麼 | 不可以 |
|---|---|---|
| 協調者 | 記錄決策和故障；轉達負責人的裁決；唯一會推送的角色 | 寫程式、評建置的成品 |
| 後端 | API、資料管線、資料庫、測試 | 給自己的成品打分數 |
| 前端 | 畫面和建好的頁面 | 給自己的成品打分數 |
| 評審 | 看做出來的東西：每一次建置、每一頁要公開的文字，在負責人看到之前先把關 | 寫程式、改它把關的那些頁面、執行任何會改動 repo 的 git 指令 |
| 稽核 | 看改動本身：每一份 diff，以及任何從外面進來的東西（工具、腳本、技能） | 寫程式、執行任何會改動 repo 的 git 指令 |
| 跑模型的 | 在有顯示卡的那台機器上：評估輪、整批分類、產生圖片 | 改或 commit 這個 repo；產出的檔案交回，由另一個 session 檢查後 commit |
| 讀資料的 | 在另一台機器上：讀外部資料來源，回報內容 | 動這個 repo |

負責人握著四件事，做之前一定先問他：資安、隱私、花錢、部署到正式環境。agent 可以推薦一個選項並說明代價，不可以替他選。

## 從這裡打得開的東西

公開的：[`api/tests/`](../api/tests/) 底下的測試（77 個 Python 測試檔）、模型評估的技能 [`.claude/skills/model-eval/`](../.claude/skills/model-eval/SKILL.md)、決策頁 [`docs/decisions.md`](decisions.md)、[`evaluation/`](../evaluation/) 底下的評估報告和答案卷。

私有的：commit 前的檢查程式、角色的指示檔、完整的決策日誌、故障登記簿。這一頁提到這些時會標「私有」，那一部分你只能相信這裡的描述。

## 程式碼強制的部分

- **每次 commit 前跑九道檢查**（私有；一個 git hook，對準備提交的檔案跑）。任何一道有發現，這次 commit 就被拒絕：長得像金鑰的字串；`app/` 底下的檔案指到外面；隨產品附帶的字型畫不出來的字；前端沒有對應的伺服器訊息或狀態碼；README 圖片裡太小的字，或圖片裡跟來源檔對不上的數字；ruff 回報的 Python 錯誤類別；故障編號亂序或重複。
- **commit 訊息也有一道檢查**（私有）：動到 `app/` 的 commit，訊息裡不能有角色名稱、故障或決策編號、人名，因為這種 commit 連同訊息一起公開。
- **發布腳本拒絕 `--push`**，除非同一行親手打上要發布的那個 commit 的 sha（私有）。
- **伺服器在錯的 schema 上拒絕啟動。** 資料庫不在最新版本、或拒絕登入時，API 程序直接結束（[`api/src/upto/schema_guard.py`](../api/src/upto/schema_guard.py)）。
- **資料庫權限有測試**，包含每個登入身分不可以讀什麼（[`api/tests/test_role_grants.py`](../api/tests/test_role_grants.py)）。

## 只靠流程強制的部分

- **發布之前**，候選 commit 上會人工跑完整套測試，包含要建資料庫的那些；`main` 要等這些都過、再由負責人親手輸入確認碼才會前進。程式碼裡沒有任何東西能擋住沒測過的 commit 被推上去。
- **評的人和做的人分開。** 評審 session 把關每一次建置和每一頁要公開的文字，做的人從不給自己打分數。這是各 session 遵守的規則，沒有任何檔案鎖定在強制執行。
- **日誌。** 每個決策都寫下代價和被放棄的選項；每次故障都登記一個編號，有對應的測試或檢查時也一併寫上（私有；到 2026-10-13 共 109 條）。公開的 [`docs/decisions.md`](decisions.md) 放的是有量測數字的那些。

## 這套流程抓到的三件事

- **一個被裁決反轉的斷言。** [`api/tests/test_trip_integration.py`](../api/tests/test_trip_integration.py) 的一部分所斷言的東西，在測試寫好的同一天就被一個裁決反過來了。2026-09-07 新加的一道檢查，讓一個不在清單上的測試也被跑到，因此抓到這一處；測試已改成依照現行的裁決來斷言。
- **一次 schema 改動弄壞的測試資料。** 把登記的測試整套跑一遍時，發現一次 schema 改動弄壞了 [`api/tests/test_preference_integration.py`](../api/tests/test_preference_integration.py) 的測試資料。修的只有測試本身，產品沒有動。從 2026-10-10 起，每次發布前都會人工跑全部的資料庫測試。
- **一條守衛沒蓋到的刪除路徑。** 重播測試（[`api/tests/test_ingest_replay.py`](../api/tests/test_ingest_replay.py)，2026-08-17）發現 `TRUNCATE … CASCADE` 會繞過那些拒絕 `DELETE` 的守衛。隔天的遷移 [`0020_truncate_guard`](../api/migrations/versions/0020_truncate_guard.py) 把它補上，測試現在兩種拒絕都會確認。

## 還沒證明的事

- **猜想：五個常駐 session 加上中間的關卡，比「一個 agent 做一張票」好。** 也就是說，比起每張票開一個 agent、各在自己的工作副本裡做，退化會比較少、負責人要介入的次數也比較少。實驗已經寫好、事先登記（同樣的任務、同樣的模型和強度、盲評、數退化次數、介入次數和成本）。如果單一 agent 分數相同或更好、成本還更低，這個猜想就被推翻。到 2026-10-13 為止，實驗還沒有跑。
- **任何一個可靠性的數字。** 有故障登記簿和決策日誌，但沒有量過退化率、變更失敗率或復原時間，也沒有「導入這套做法之前」的時期可以比。
- **獨立性有極限。** 做的人、稽核、評審是同一個模型家族的不同 session；測試是寫程式的那些 session 自己寫的。commit 前的檢查可以用 `git commit --no-verify` 跳過，檢查程式本身也是任何 session 都改得動的一般檔案。擋在這些和 repo 之間的，是審查和 git 的歷史。
