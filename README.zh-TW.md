**一群人一起決定一餐。選的是一對加權的骰子。**

給一群永遠喬不定去哪吃的朋友。他們想看到一家店為什麼贏，一份排名說服不了他們。

**試用：[uptoyou.jacksong-tw.com](https://uptoyou.jacksong-tw.com)**

### 開一局試試

```sh
docker compose run --rm migrate                          # the schema, once per version
docker compose up -d --wait                              # the stack
docker compose exec api python -m upto.issue 1 Kevin     # a device token, printed once
```

打開 `localhost:8080`，貼上 token，提三家店，擲。

## 這個專案在解決什麼問題？

### 1. 沒有人想當做決定的人

幾個朋友要吃晚餐。每個人都有一點偏好，可是沒有人想扛這個決定。結果要嘛聽最大聲的那個，要嘛花二十分鐘決定不了。

### 2. 排名只是把爭論搬家

軟體通常的答案是排名。排名只是把爭論搬到別處。大家改成爭這份排名對不對。從排名裡挑的那個人，還是得扛這個選擇。

## 為什麼用「加權骰子」？

骰子天生公平。沒有人挑，所以沒有人需要替結果辯護。那個社交問題就這樣解決了，靠的是規則本身。

可是純粹的骰子會忽略這群人知道的一切。所以骰子要加權。每家店分到三十六種結果裡的一份。重要的事會移動這一份。有人避開的類型是**折扣，不是否決**，而且和桌上的人數成比例。桌上有 N 個人時，一個人反對，那家店少掉 1/N 的機率。N = 5 時少掉五分之一，那家店仍然抽得到。N = 1 時就是否決，因為一個人的一局就是那個人的決定。

![The reveal — the winner, and every factor that moved its odds](docs/reveal-panel.png)

加權的骰子，要看得到權重才值得相信。每個因素都是一列存下來的資料，記著它從哪一筆讀數算出來。開獎不會為了顯示再算一次。它讀擲骰時用的那幾列，然後一列一列念出來。

「請你相信」和「你可以查」，差別就在這裡。這也是為什麼偏好進來時私密，出去時看得見。移動機率的東西會顯示。誰要求的，不顯示。

**而且隱私是在資料庫裡執行的，不是介面口頭保證的。** 關閉一個回合會觸發一個 trigger，在讓結果落地的那個交易裡，把 `proposal.member_id` 設成空值 —— 手動用 SQL 關閉、或一個修補腳本，都會把作者身分留下來，而且都不會報錯。寫入一個偏好會回 204 而且**完全不發出事件**，因為在一個小圈子裡，一個事件發生的時刻離一個名字只差一次猜測。偏好預設只存在於這一餐，每晚由一個只能讀和刪那一張表、其他什麼都不能做的角色抹除。

## Up to you 的解法

每個因素都乘上一家店在三十六種結果裡的那一份。這些數字存在資料庫裡，開獎時直接讀。

| 因素 | 對一家店的機率做什麼 | 為什麼 |
|---|---|---|
| 它那一區在下雨 | 降低。基準是今晚池子裡最乾的那一區 | 下雨天走過去是真的成本。這是今晚的事實，跟店本身無關 |
| 這個圈子上禮拜去過 | 砍一半 | 換換口味，但選項還在。只有簽過的行程算數，只被擲到、沒簽的店不受影響 |
| 有人避開它的類型 | 降低 1/N，N 是桌上的座位數 | 這是折扣。五個座位裡一票反對，和兩個座位裡一票反對，效果不同 |
| 什麼都沒發生 | 不動它 | 起點的權重是 1。沒有作用的因素會畫成一列空的，不會消失 |

## 專案特色

- **35,965 家店**，來自七個公開政府來源。每次抓取都以內容定址，沒變的檔案不花成本。
- **一個分類器，在凍結的 200 列集合上評分**。四個地端模型在上面比較：72.0 · 71.0 · 70.5 · 65.5。
- **每個因素都是一列存下來的資料**。成員在開獎時讀得到，也查得到它來自哪一筆讀數。

## 關鍵技術決策

### 1. 店名：清洗、解析，真正的難點

**難點** 知道有哪些選擇之後，決定很容易。知道有哪些選擇，才是工作。登記名稱指的是法人，你認得的是招牌。政府的餐飲名單知道的是 安心食品服務股份有限公司。要決定去哪吃的人知道的是 摩斯漢堡。這是同一家公司。只有其中一個名字一般人認得出來。

![The name ladder — sign, then brand, then registered name](docs/diagrams/name-ladder.png)

**做法** 顯示名稱分三層找：先找稽查員記下的招牌，再找品牌，最後才用登記名稱。三個來源用登記號 join，優先順序固定，完全不做模糊比對。否決掉的是只用登記名稱，還有跨來源做字串相似度。

**結果** 登記名稱裡有 40.2% 是法人字串，根本沒有指涉任何一家店。有招牌的那些列裡，招牌和登記名稱有 93% 不一樣。品牌表把它涵蓋到的公司改掉了 57%。試用過一個外部地理資料來源，只靠地址就錯誤 join 了 46%，所以放棄。店名階梯碰得到多少，2026-09-11 量在目前這一版參考名單的 36,376 列上：

| 階 | 列數 | 佔比 | 其中仍然是公司名的 |
|---|---|---|---|
| 招牌（店面層級） | 1,363 | 3.7% | 3.2% |
| 品牌（只限單一品牌公司） | 4,003 | 11.0% | 44.2% |
| 登記名稱（剩下的） | 31,010 | 85.2% | 32.9% |

這道階梯碰到全市的 14.8%。全部列裡有 33.1%，顯示出來的字串仍然是公司名。有招牌的地方，名字就是對的。每二十七列有一列有招牌。

### 2. 分類：RAG

**難點** 沒有任何公開來源說一家店賣什麼。沒有一個官方欄位寫著「這是一家麵店」。所以分類是生成出來的，用的是 RAG（檢索增強生成）。問模型之前，先用向量搜尋找出五個名字最像、而且已經有正確分類的店家。這五家連同要分類的名字一起給模型當範例。模型讀的是這個專案能找到的最佳店名（階梯最上層那一個），從十三個分類裡選一個。它的正確率是在一個凍結的集合上量出來的。

**做法** 分三步。檢索：用 pgvector 找出五個最像的已標記名字。增強：把這五個放進提示，當作示範題。生成：模型回答一個分類。標註過的範例名字嵌入 pgvector，就是這裡說的範例集。缺少的知識用資料補，提示詞和權重都不動。否決掉的是再改一版提示詞，還有微調。分類跑在地端的 3B 模型上：一個量化的 3B 生成模型，跟資料庫同一台，只做批次，沒有回填時就關著。雲端模型只當比較基準。否決掉的是用託管模型當分類器。免費的託管額度一天 500 次呼叫，3,300 家店要七天。地端模型一個晚上做完。託管模型的分數留著，當作地端模型對照的那條線。

**結果**

![The evaluation loop — how a classifier candidate is scored](docs/diagrams/evaluation-flow.png)

*同樣 200 列凍結的資料，每個模型跑一輪，評完分就不再重跑。*

改提示詞那一版在固定集合上*掉*分（51.5 → 49.5）。同一個集合上加檢索，`gemma2:2b` 從 51.5 → 61.0，`llama3.2:3b` 從 37.0 → 58.0。`qwen2.5:3b` 卻是 51.0 → 48.5。同一個範例集，對其中一個模型是雜訊。所以模型和範例集的配對是量出來的。

*目前的表*：提示詞 v7、十三個分類、`testset_v3`。範例集同一個（`snowflake-arctic-embed2`、五個鄰居）。每一輪都在家裡那台機器上跑，走排程任務用的同一個中繼：

| 模型 | 授權 | 匯總正確率（200 列） |
|---|---|---|
| `qwen2.5:7b-instruct` | Apache-2.0 | **72.0%** |
| `gemma2:2b` | Gemma terms | 71.0% |
| `llama3.2:3b` | Llama 3.2 community | 70.5% |
| `qwen2.5:3b-instruct` | 研究授權，只能評測 | 65.5% |

三個模型彼此差不到兩分。其中一個每列的成本是三倍。排程任務留下 `gemma2:2b`。託管的比較基準只在第一個集合上量過，60.5%。

### 3. 官方行業代碼能決定什麼

**難點** 稅籍登記有行業代號。它只決定它能決定的，大約十列裡只有一列。

**做法** 稅籍代號在明確的時候說了算，其他交給模型。否決掉的是用代號當分類器，還有完全不理代號。

**結果** 代號可以定全市 10.9% 的列。一家咖啡連鎖的 245 家分店登記在批發代號底下，只看代號會把每一家都標錯。join 本身是安全的：去掉法人形式的字尾之後，名稱一致率 99.78%。地址就不安全，89.8% 不一樣。[長版本](docs/decisions.md)把同一個問題拿到那 200 列評分資料上量，站得住腳的上升空間是 +4 列。

### 4. 資料匯入：內容定址與執行紀錄

**難點** 每個來源自己決定什麼時候更新。沒有變化的日子，也要分得出「沒變」和「壞了」。

**做法** 每個抓下來的檔案一列發佈，每一筆記錄一列資料。另外一本執行紀錄，沒有變化的那一天寫一次心跳。否決掉的是就地覆寫，還有用猜的排程去配合每個檔案的更新頻率。

**結果** 每個來源在位元組相同時重跑，結果都一樣。每一張表的每一個欄位都比對過，走真正的命令列入口跑兩次。在參考來源上，沒有變化的路徑花 1.6 秒，真的要存花 15.0 秒。各來源的數字在下面那張表，散得比這一對寬很多。

*量在排程本身上*：8 天、332 列執行紀錄，對上 361 個 Airflow task instance。沒有加任何量測工具，沒有加任何欄位：

| 來源 | 有存 p50 | 沒變化 p50 | 執行紀錄列數 |
|---|---|---|---|
| 中央氣象署 鄉鎮預報 | 2.99 秒 | 1.85 秒 | 149 |
| 中央氣象署 測站觀測 | 3.09 秒 | 0.31 秒（n=1） | 149 |
| 食藥署 餐飲場所 | 還沒有 | 1.88 秒 | 5 |
| 食材登錄 品牌 | 0.57 秒 | 0.96 秒 | 8 |
| 衛生評核 招牌 | 0.31 秒 | 0.43 秒 | 7 |
| 商業登記 狀態 | 25.03 秒 | 2.09 秒 | 7 |
| 營業稅籍 | 12.95 秒 | 3.58 秒 | 7 |

**在最大的來源上，沒有變化的一天比有存便宜 3.6×**，在名冊上是 12×。這就是「先搶再解析」這條捷徑省下的成本。**排程本身每個任務固定花 1.2 秒**，來源花半秒或二十五秒都一樣。**排程器不是瓶頸：**全部 361 個任務的佇列延遲 p50 是 0.05 秒，最差 4.2 秒。這些數字回答不了抓取、解析、儲存各花多少，因為沒有任何東西記錄它。

### 5. 觀測性

- **串流的心跳是每 25 秒一行註解。** 安靜超過 130 秒，前面的 proxy 會把串流切掉。它不帶任何成員讀得出來的時間資訊。
- **每個 API 行程對資料庫持有一條監聽連線**，事件從這條連線散出去。所以不只一個行程可以服務同一個圈子。那條連線死掉時，這個行程會說出來：`/health` 回 503，帶著 `stream_listener` 和掛掉的時間。讀取照常服務。在一次真的砍連線上量到：**0.18 秒內回 503，1.23 秒內在新連線上恢復。**

### 6. 可靠性

- **API 行程不會去服務一個它不是照著寫的 schema。** 它在啟動時讀 migration 版本。資料庫落後、超前、或從來沒 migrate 過，它就把兩個版本寫進 log，然後結束。所以部署會在錯的那個 container 上失敗，錯誤到不了成員的請求裡。
- **對模型的連線會重試，重試次數會印出來。** 這條路徑上，一個冷的模型看起來是*掛掉*，看不出是慢：第一個請求失敗，十二秒後重試，半秒就回。一條不穩的連線在紀錄裡是一個數字，而不是一個很慢的晚上。
- **排程任務失敗會送一則訊息。** 訊息帶 log 在 container 裡的路徑，永遠沒有 URL。全新 clone 預設關掉通知。另外有一個故意會失敗的任務，用來測這個通道本身。
- **每個來源都被證明是冪等的，不是假設的。** 每一個都走它真正的命令列入口跑兩次，每一張表的每一個欄位都比對。沒有變化的一天是一個被記錄下來的結果，不是一個空白。
- **68 個測試檔案**，兩種節奏：host-side 不需要網路也不需要資料庫；build-and-drop 自己建資料庫，跑在唯一握有擁有者憑證的那個服務裡。每一次 commit 還要通過 pre-commit hook 裡的六道本地檢查，其中五道只需要標準函式庫，所以一個 clone 不需要任何工具鏈就能 commit。

### 其他六個決定

- **向量搜尋是 Postgres 的擴充，不另外開服務。** 範例集是三個嵌入模型合計 537 列。為這些列多養一個有狀態的服務，還要備份、要監控，不值得。
- **評測集合是凍結的、分層的，標註者是誰有寫出來。** 它抓到一版提示詞，讀起來更好，分數卻更差。固定集合存在的唯一理由就是這個。
- **子字串搜尋維持循序掃描。** trigram 索引在 31 個實際查詢裡改變了 0 個執行計畫。真正的成本是一個 lateral，每按一鍵執行 35,533 次。
- **那台小機器扛不住自己的夜間工作。** 一個匯入之下剩 49 MB，變成最差 398 MB。整套 stack 靜置從 1,131 → 1,009 MiB。
- **雲端負責服務，家裡那台負責算。** 一張 8 GB 的顯示卡處理帶檢索的批次，一個名字 0.92 秒。同一台機器的 CPU 要 12–19 秒。
- **即時串流會送心跳。** 經過 proxy，一個安靜 130 秒的串流會被切斷。之後真的有事件也送不到。

[長版本](docs/decisions.md)有這六個的完整內容。另外寫了每個來源存什麼、十三個分類、清單外的答案怎麼被拒絕。凍結的評測集合怎麼抽出來，也在那裡。

## 限制與未來方向

只有臺北：十二個行政區、一個城市的開放資料，地址在匯入的邊界就正規化，因為同一份政府檔案把市名寫成兩種寫法。**每一個來源都在它的授權範圍內使用** —— 授權是非商業或不確定的來源就完全不用，整條管線裡沒有任何評分、任何評論、任何爬來的頁面。尺寸是給一個小團體的，房間狀態存在行程裡。這是一個作品集專案，在一個私有 repository 裡開發，每次合併之後抽出到這裡，所以 commit 訊息帶著每一次改動背後的理由。

- **素食 從分類改成一家店帶著的屬性**（素食麵館 = 麵食 + 有素）。「我不能在這裡吃」是桌上的一個需求，折扣處理不了。分類集合回到十二個。
- **不只一個行程，前面放負載平衡器。** 事件匯流排已經在資料庫裡，schema 那一步也已經是部署的一步。
- **用 MLflow 管評測回合**，取代回合檔案自己手寫的記帳。
- **超市 分類與提示詞 v8。** 測試集必須先重抽，否則新的分數跟現在這個不能比。
- **文字轉語音與語音轉文字的評測回合**，給一支介紹影片用。評分方式跟分類器一樣：固定集合、先查授權、每個候選一個數字。

## 快速開始

```sh
cp .env.example .env                # names only — the comments state the shape of every value
docker compose run --rm migrate     # the schema, once per version
docker compose up -d --wait         # the stack
curl -s localhost:8080/health
#   {"status":"ok","database":"reachable","instance":"…","stream_listener":"up"}
```

**兩個指令。** schema 那一步離開了整套 stack 的開機流程，好讓多個行程不會搶它。migrate 是冪等的 —— 對一個已經是最新的資料庫跑，它什麼都不會做。

`localhost:8080` 是這個 app；API 和資料庫只在 compose 網路裡面連得到。氣象匯入需要一把免費的中央氣象署開放資料金鑰（opendata.cwa.gov.tw），在 init 時讀一次進 Fernet 加密的 Airflow Connection，另外五個開放資料檔案不需要任何憑證。新的排程任務會以**暫停**狀態出現。

手動跑匯入、跑分類回填、跑測試、用血緣工具：[docs/operations.md](docs/operations.md)。
