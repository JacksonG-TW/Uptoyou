**一群人一起決定一餐，由一對加權的骰子來選。**

給一群永遠喬不定去哪吃的人 —— 而且他們寧願看見一家店為什麼贏，也不想被叫去相信一份排名。

**試用：[uptoyou.jacksong-tw.com](https://uptoyou.jacksong-tw.com)**

### 開一局試試

```sh
docker compose run --rm migrate                          # the schema, once per version
docker compose up -d --wait                              # the stack
docker compose exec api python -m upto.issue 1 Kevin     # a device token, printed once
```

打開 `localhost:8080`，貼上 token，提三家店，擲。

## 看它動起來

![A round from start to finish — propose, roll, reveal](docs/reveal-walk.webp)

五個畫面，每個只做一件事：

- **首頁** —— 圈子，以及今晚開著的那一局。
- **裝置** —— 貼一次 token；瀏覽器記住這個圈子。
- **這一餐** —— 今晚要避開的類型，做成帶分節記號的選單。
- **回合** —— 提店，然後擲。
- **開獎** —— 骰子停下，然後贏家的機率被一項一項拆開。

## 這個 app 解決什麼問題

五個朋友要吃晚餐。每個人都有一點偏好，可是沒有人想扛下這個決定，所以這群人不是聽最大聲的那個，就是花二十分鐘
決定不了。軟體通常的答案是排名，而排名只是把爭論搬到「這份排名對不對」上面。

這個 app 改成擲骰子 —— 但骰子是加權的，而且權重看得見。某一區下雨，那一區的機率就低一點。上禮拜去過的店砍
一半。有人默默避開的類型，會讓那家店損失一部分機率，比例跟桌上有幾個人有關，所以五個人的時候，一個人反對是
折扣而不是否決。

**上面每一個因素都是一列存下來的資料，並釘住它是從哪一筆讀數算出來的。** 開獎不會為了顯示而重算：它讀的就是
擲骰時用的那幾列，然後把每一列念出來。這就是「請你相信的結果」和「你可以查核的結果」之間的差別 —— 也是為什麼
這個 repository 真正有意思的地方是產生那些讀數的資料管線，而不是骰子。

## 名詞

| 名詞 | 在這裡的意思 |
|---|---|
| **圈子（Circle）** | 一群固定會一起吃飯的人。 |
| **成員（Member）** | 一個人在一個圈子裡的位子。沒有帳號、沒有 email —— 一個裝置 token。 |
| **回合（Round）** | 正在決定的一餐。開局、收提名、以一次擲骰結束。 |
| **提名（Proposal）** | 某人在這一局提出來的一家店。 |
| **擲（Roll）** | 兩顆骰子，由這一局的因素加權。只有一次算數，而且在看到骰子之前就先講好是誰。 |
| **開獎（Reveal）** | 擲完之後的畫面：贏家，以及每一個移動過它機率的因素。 |
| **貢獻（Contribution）** | 一個存下來的因素 —— 它乘了多少、是哪個貢獻者產生的、來自哪一筆讀數。 |
| **店（Place）** | 一家餐廳。可能來自公開的參考名單，也可能是某個圈子自己加的。 |
| **發佈（Publication）** | 一次抓下來的檔案，用位元組的雜湊值當身分。永不覆寫。 |
| **匯入紀錄（Ingest run）** | 對一個來源的一次嘗試。記錄發生了什麼，包含「什麼都沒變」。 |
| **店名階梯（Name ladder）** | 顯示名稱怎麼挑：招牌、然後品牌、然後登記名稱。 |
| **分類（Category）** | 一家店可以被分到的十三個封閉值之一。 |
| **範例庫（Crib）** | 從 pgvector 取出、當作示範題交給分類器的標註範例。 |

## 改了什麼，量了多少

六個做了改動、而且兩邊都量過的數字。

| 項目 | 之前 | 之後 | 量在哪裡 |
|---|---|---|---|
| 沒有新檔案的那一天 | 15.0 秒 | **1.6 秒** | 流水帳，8 天，7 個來源 |
| 為範例庫嵌入一個名字 | 0.481 秒 | **0.045 秒** | 100 個名字，量兩次，09-04 |
| 分類一個名字 | CPU 上 12–19 秒 | 8 GB 顯示卡上 **1.27 → 0.92 秒** | 一個行政區，1,318 列 |
| 名冊匯入的記憶體峰值 | 172 MB | **77 MB** | 一台 2 GB 機器，09-05 |
| 服務中的整套 stack 靜置 | 1,131 MiB | **1,009 MiB** | 一台 2 GB 機器，09-07 |
| 一次長時間的分類 | 頭尾差 1.7× 變慢 | **平的** | 36,014 列、10.5 小時，09-03 |

記憶體的數字是在當時那台 2 GB 機器上量的；那台機器後來已經換大。[長版本](docs/decisions.md)有後面四項的
推演過程。

## 架構

![Architecture — the stack as it is served](docs/diagrams/architecture.png)

*一台主機、一個 compose 檔。Cloudflare 在邊緣終結 TLS，來源端用自己的憑證回應；四個 Airflow 服務和
API 共用同一個 PostgreSQL，各自用自己的角色連線。*

| 層 | 跑什麼 |
|---|---|
| **前端** | Vite + React 19 + Tailwind 4 + shadcn/ui，在 proxy image 裡面 build。沒有 CDN、執行時不抓任何東西；兩套子集字型跟著 bundle 一起出貨。 |
| **API** | Python、FastAPI、SQLAlchemy 2.0，全程 async，43 個手寫的 Alembic migration。 |
| **資料庫** | PostgreSQL 17。五個登入角色，一個邊界一個：API、匯入、每晚的抹除、備份，以及擁有者 —— 只有那個一次性的 migration container 拿得到擁有者。 |
| **向量** | pgvector，就在同一個資料庫裡。 |
| **排程** | Apache Airflow 3、LocalExecutor，在同一套 compose 裡。它的中繼資料是同一個 PostgreSQL 裡的第二個資料庫。 |
| **模型** | Ollama 跑在家裡那台的 8 GB 顯示卡上，透過一個中繼連過去。`gemma2:2b` 生成、`snowflake-arctic-embed2` 檢索。 |
| **部署** | 東京一台 EC2，前面是 Full (strict) 模式的 Cloudflare。它從公開 registry 拉 image，自己不 build。 |

## 資料

![The ETL pipeline — seven sources into one ledgered store](docs/diagrams/etl-flow.png)

*七個公開來源、六個匯入；氣象發佈者的預報和觀測是同一次抓取裡的兩個來源。每一次抓取都以內容定址，每一次執行
都被記錄，包含什麼都沒做的那些。*

| 排程（UTC） | 臺北 | 來源 |
|---|---|---|
| 每小時 | 每小時 | 中央氣象署 鄉鎮預報 `F-D0047-061` + 測站觀測 `O-A0001-001` |
| `0 19 * * *` | 03:00 | 食藥署 食品業者登錄 —— 餐飲場所參考名單 |
| `20 19 * * *` | 03:20 | 臺北市食材登錄平台 —— 公司 ↔ 品牌對照 |
| `40 19 * * *` | 03:40 | 臺北市餐飲衛生分級評核 —— 稽查員看到的招牌 |
| `0 20 * * *` | 04:00 | 商業登記-餐館業 —— 哪些登記已經停業 |
| `20 20 * * *` | 04:20 | 財政部 全國營業(稅籍)登記 —— 稅籍名稱 + 行業代號 |
| `0 21 * * *` | 05:00 | 刪掉每一列沒有被擲骰釘住的單餐偏好 |
| `40 21 * * *` | 05:40 | 刪掉沒被釘住、超過九十天的氣象讀數 |
| `20 22 * * *` | 06:20 | 兩個刪除工作之後 `pg_dump` 到 S3，保留三十份 |

cron 都是 UTC，而它們瞄準的離峰時間是臺北的 —— 每日來源在臺北時間 03:00 到 04:20 之間抓，一次下載一個。

**一次發佈的身分是它位元組的雜湊值，不是時間戳。** 時間戳可能在資料沒動的時候動，也可能在資料動了的時候不動。
檔案自己帶時間戳的時候，它會被放在雜湊值旁邊當標籤，而且每一次執行都比對；兩者不一致就刻意讓那個任務失敗。

**便宜的那一半守住貴的那一半。** 參考名單的匯入抓一個 17 MB 的 zip，對壓縮後的位元組取雜湊，然後用
`insert … on conflict do nothing returning id` 去搶那筆發佈 —— 由*資料庫*決定這份內容是不是新的。只有這樣
之後，才有人會去解壓縮裡面那個 99 MB 的 CSV。那個檔案是月更的、輪詢是每天，所以一個月大概有 29 次什麼都找
不到，而且必須安靜地成功。

**什麼都沒寫的一次執行仍然是一次執行。** 每一次嘗試都寫一列，而且「沒有變化」和「失敗」是不同的、被記錄下來
的結果。從「沒有」去推論，這兩者分不出來 —— 而那就是一個壞掉的來源可以看起來健康一整個禮拜的原因。

### 存了什麼

| | |
|---|---|
| **店** | 服務中的機器上有 35,965 家，其中 25,031 家帶有生成的分類。 |
| **稅籍** | 一個 66 MB 的 zip，裡面一個約 320 MB 的 CSV、1,711,012 列 —— 全國每一家有登記的公司行號。只有 統編 已經出現在最新一次參考發佈裡的列會被存下來：**19,203 個參考統編裡對上 14,521 列，大約 15 秒。** |
| **招牌與品牌** | 1,686 列稽查員記下的招牌（其中 1,379 列對上目前的發佈）；288 列公司 ↔ 品牌。 |
| **氣象** | 每小時的預報與觀測讀數，保留九十天，除非被某次擲骰釘住。 |
| **範例庫** | 每個嵌入模型 537 列標註過的範例名字，放在 pgvector。 |

稅籍發佈了別的來源都沒有的東西 —— 稅捐機關持有的 營業人名稱，以及**這家公司自己登記的 行業代號**，一個店家
自己選的官方分類，而不是模型猜的。四組代號／名稱是按位置存的：第一組是主要營業項目，把空的尾巴壓掉會悄悄
把次要的升成主要的。schema 裡留了一個警告 —— `business_tax_row.address` 是*登記*地址，不是店面地址（對上的
列裡有 13.7% 不在 臺北市），而且任何東西都不可以用它來 join。

### 店名與分類

**登記名稱是一個法人，不是一家店。** 參考名單知道的是 安心食品服務股份有限公司；要決定去哪吃的人知道的是
摩斯漢堡。所以顯示名稱在讀取時沿著一道階梯解析 —— **招牌 → 品牌 → 登記名稱。** 招牌贏：稽查員是對著同一個
登記號記下來的，所以那個 join 完全不需要比對名字。品牌只在一家公司剛好只對到一個品牌時適用，因為兩個來源都
沒有說一家多品牌公司的這個點是哪一個品牌。登記資料記為停業、而且從來沒有營業過的 統編，會從搜尋建議裡消失。

量在目前這一次發佈的 36,499 列上，那是已發佈的列數，不是服務中的機器上那 35,965 家店 ——
[長版本](docs/decisions.md)把這三個數字對起來。

| 階 | 列數 | 佔比 | 其中仍然是公司名的 |
|---|---|---|---|
| 招牌（店面層級） | 1,379 | 3.8% | 3.3% |
| 品牌（只限單一品牌公司） | 4,001 | 11.0% | 44.0% |
| 登記名稱（剩下的） | 31,119 | 85.3% | 33.3% |

**這道階梯碰到全市的 14.7%，而且全部列裡有 33.3% 顯示出來的字串仍然是公司名而不是店名。** 有招牌的地方名字
就是對的，而每二十六列裡有一列有招牌 —— 這是下一個來源的理由，不是這個來源的反證。接著推導會把那些沒有招牌、
否則會撞在一起的列拆開：9,136 列加上行政區與路名的括號、3,234 列還需要門牌號、22,750 列是該公司唯一沒有招牌
的點，就保持原樣。

**分類是十三個封閉的值：** 麵食 · 飯食 · 小吃 · 火鍋 · 燒烤 · 日式 · 西式 · 早餐 · 咖啡飲料 · 便利商店 ·
台菜 · 素食 · 其他。不在清單裡的答案是**被拒絕，而不是被修好** —— 把 拉麵 硬塞成 麵食 是把一個錯的答案變成
一個像樣的答案，而且刪掉了整個流程裡唯一會失敗的那一步。

分類是對著一個本地部署的量化模型批次跑的，沒有在回填的時候就是關著的。模型被問的是這個專案握有的最好的名字
—— 同一道階梯 —— 而且每一列決定過的資料都記下**提示詞版本、模型名稱，以及實際被問的那個字串**。判定為法人
會被寫成一個「決定過的沒有」：來源在、分類是空的，所以重跑永遠不會再問一次。批次邊跑邊 commit，所以一個被中斷
的七小時任務會從停下來的地方繼續。

**是設計來被量測的，不是用講的。** `evaluate/testset_v3.json` 是一個凍結、由教師模型標註的 **200 個名字**的
集合 —— 標籤由一個前沿模型起草、再由第二個模型交叉檢查，所以分數讀作「與教師的一致程度」，永遠不是絕對正確
—— 而且是一次抽定的：固定亂數種子、依照名字來自階梯的哪一階做分層、每層至少 30 筆。這個抽樣從來沒有重跑過；
v1 和 v2 是同樣 200 列重新標註的版本，保留是因為對著它們跑出來的分數仍然成立，而且每一份報告都寫明它的集合
和 sha256，所以兩個數字只有在兩邊都對上時才可以比較。

## 主要技術決策

十一個選擇，每一個都寫出被否決的那條路，以及決定它的那個數字。

![The evaluation loop — how a classifier candidate is scored](docs/diagrams/evaluation-flow.png)

*同樣 200 列凍結的資料，每個模型跑一輪，評完分就不再重跑。*

**1. 分類跑在地端的 3B 模型上；雲端模型是尺，不是工人。**
*選擇：*一個量化的 3B 生成模型，跟資料庫同一台，只做批次，沒有回填的時候就關著。*否決：*用託管模型當分類器。
*那個數字：*免費的託管額度一天 500 次呼叫，所以 3,300 家店要七天；地端模型一個晚上做完 —— 而託管模型的分數
留著，當作地端模型被對照的那條線。

**2. 缺少的知識是用資料補的，不是用提示詞或權重。**
*選擇：*一個檢索範例庫 —— 標註過的範例名字嵌入 pgvector，最近的五個當作示範題交給模型。*否決：*再改一版提示
詞；微調。*那個數字：*改提示詞那一版在固定集合上*掉*分（51.5 → 49.5）；同一個集合上加檢索讓 `gemma2:2b`
從 51.5 → 61.0、`llama3.2:3b` 從 37.0 → 58.0，而 `qwen2.5:3b` 是 51.0 → 48.5 —— 同一個範例庫對其中一個模型
讀起來是雜訊，所以這個配對是量出來的，不是假設的。

*目前的表* —— 提示詞 v7、十三個分類、`testset_v3`、同一個範例庫（`snowflake-arctic-embed2`、五個鄰居），
每一輪都在家裡那台、透過排程任務用的同一個中繼：

| 模型 | 授權 | 匯總正確率（200 列） |
|---|---|---|
| `qwen2.5:7b-instruct` | Apache-2.0 | **72.0%** |
| `gemma2:2b` | Gemma terms | 71.0% |
| `llama3.2:3b` | Llama 3.2 community | 70.5% |
| `qwen2.5:3b-instruct` | 研究授權 —— 只能評測 | 65.5% |

三個模型彼此差不到兩分，其中一個每列的成本是三倍；排程任務留下 `gemma2:2b`。託管的那把尺在第一個集合上是
60.5%，沒有在第三個集合上重跑過，所以這兩個數字不會被寫進同一句話。

**3. 向量搜尋是 Postgres 的擴充，不是第二個服務。**
*選擇：*在這套 stack 已經有的資料庫上用 `pgvector`。*否決：*一個專門的向量資料庫（Pinecone、Milvus、
Qdrant）。*那個數字：*範例庫是三個嵌入模型（`bge-m3`、`qwen3-embedding:0.6b`、`snowflake-arctic-embed2`）合計 537
列 —— 最多也就幾千 —— 對上多一個要跑、要備份、要監控的
有狀態服務。

**4. 評測集合是凍結的、分層的，而且它的標註者身分有寫出來。**
*選擇：*200 個名字、固定亂數種子、依三階店名分層且每層至少 30 筆、由教師模型標註並經第二個模型交叉檢查、
每一列都記下來源。*否決：*對著即時資料評分；只由擁有者標註。*那個數字：*這個凍結集合抓到了一版讀起來更好、
分數卻更差的提示詞，而那正是固定集合存在的唯一理由；每一份報告都帶著集合的 sha256，所以兩個分數只有在它對上
時才可以比較。

**5. 一家店的名字沿著階梯解析 —— 招牌、然後品牌、然後登記名稱。**
*選擇：*三個來源用登記號 join、優先順序固定、完全不做模糊比對。*否決：*只用登記名稱；跨來源做字串相似度。
*那個數字：*登記名稱裡有 40.2% 是根本沒有指涉任何一家店的法人字串；有招牌的那些列裡，招牌和登記名稱有 93%
不一樣；品牌表把它涵蓋到的公司改掉了 57%；而試用一個外部地理資料來源，只靠地址就錯誤 join 了 46%，因此放棄。

**6. 官方行業代號只決定它能決定的，而那是十列裡的一列。**
*選擇：*稅籍代號在明確的時候說了算，其他交給模型。*否決：*用代號當分類器；完全不理代號。*那個數字：*代號
可以定全市 10.9% 的列，而一家咖啡連鎖的 245 家分店登記在批發代號底下 —— 只看代號會把它們每一家都標錯。join
本身是安全的（把法人形式的字尾去掉之後，名稱一致率 99.78%）；地址則不是（89.8% 不一樣）。[長版本](docs/decisions.md)
把同一個問題拿到那 200 列被評分的資料上量，站得住腳的上升空間是 +4 列。

**7. 每個來源都以內容定址，而且它沒有變化的日子也被記下來。**
*選擇：*每個抓下來的檔案一列發佈、每一筆記錄一列資料，還有一本流水帳，沒有變化的那一天寫下一次心跳。*否決：*
就地覆寫；用猜的排程去配合每個檔案的更新頻率。*那個數字：*每個來源在位元組相同時都是冪等的 —— 每一張表的
每一個欄位都比對過，而且是走真正的命令列入口跑兩次 —— 而在參考來源上，沒有變化的路徑花 1.6 秒，真的要存
是 15.0 秒。各來源的數字在下面那張表，而且散得比這一對寬很多。

*量在排程本身上* —— 8 天、332 列流水帳對上 361 個 Airflow task instance，沒有加任何量測工具、沒有加任何欄位：

| 來源 | 有存 p50 | 沒變化 p50 | 流水帳列數 |
|---|---|---|---|
| 中央氣象署 鄉鎮預報 | 2.99 秒 | 1.85 秒 | 149 |
| 中央氣象署 測站觀測 | 3.09 秒 | 0.31 秒（n=1） | 149 |
| 食藥署 餐飲場所 | 還沒有 | 1.88 秒 | 5 |
| 食材登錄 品牌 | 0.57 秒 | 0.96 秒 | 8 |
| 衛生評核 招牌 | 0.31 秒 | 0.43 秒 | 7 |
| 商業登記 狀態 | 25.03 秒 | 2.09 秒 | 7 |
| 營業稅籍 | 12.95 秒 | 3.58 秒 | 7 |

**在最大的來源上，沒有變化的一天比有存便宜 3.6×**，在名冊上是 12× —— 就是「先搶再解析」這個短路，標好價。
**排程本身每個任務固定花 1.2 秒**，不管那個來源是花半秒還是二十五秒都一樣。**排程器不是瓶頸：**全部 361 個
任務的佇列延遲 p50 是 0.05 秒、最差 4.2 秒。這些都回答不了的是抓取／解析／儲存的拆分 —— 沒有任何東西記錄它。

**8. 雲端負責服務、家裡那台負責算、流水帳是時鐘。**
*選擇：*一台小 EC2 跑 API 和資料庫；模型批次跑在家裡那台，再透過同一本匯入流水帳落地。*否決：*在 EC2 上常駐
一個模型；全部批次都上雲。*那個數字：*整套服務中的 stack 靜置是 1,009 MiB，而家裡那台的 8 GB 顯示卡處理一個
帶檢索的批次是**一個名字 0.92 秒**，同一台機器的 CPU 則是 12–19 秒。[長版本](docs/decisions.md)有這件事經過
的三次量測，包括量錯東西的那兩次。

**9. 子字串搜尋維持循序掃描；trigram 索引量過之後被否決。**
*選擇：*搜尋建議的 `ILIKE '%q%'` 就維持原樣。*否決：*在三個被搜尋的欄位上加 `pg_trgm` + GIN。*那個數字：*
這個索引在 31 個實際查詢裡改變了 0 個的執行計畫，p50 從 311 → 324 ms，因為那個條件是把一個基礎欄位跟兩個
lateral 的輸出做 OR，所以過濾條件碰不到索引 —— 而且叢集用的是決定性的 `C` locale，讓 `pg_trgm` 對 96.2% 的
名字產生不出任何 trigram。掃描從來都不是成本：一個每列都重跑的 lateral 品牌查詢，每按一個鍵執行 35,533 次，
佔了這個查詢 93% 的 buffer，而把它寫成一個 grouped join 是 61× 更少的 buffer，結果可證明完全相同。

**10. 那台小機器扛不住自己的夜間工作，而修法是先量過才選的。** *選擇：*把唯一一個會把整個檔案讀進記憶體的
匯入改成串流，然後用四個設定加一個真的會咬人的記憶體上限把 Airflow 縮小。*否決：*先換大一點的機器；swap 檔，
它是把當機換成爬十二個小時。*那個數字：*一個匯入之下剩 49 MB，之後最差是 398 MB，而整套 stack 靜置從
1,131 → 1,009 MiB。[長版本](docs/decisions.md)有那一週照發生順序的記錄，包括怪錯對象的那一晚。

**11. 即時串流會送心跳，因為它前面的 proxy 會切掉安靜。** *選擇：*每 25 秒一行 SSE 註解，對每個畫面都是隱形的。
*否決：*一個不經過 proxy 的網域名稱，那等於放棄這個網域存在的那面盾。*那個數字：*經過 Cloudflare，一個安靜
130 秒的串流會**被切斷**，之後真的有事件也送不到；直接連來源端，同樣的串流維持開著而且送得到 —— 同樣的程式、
同樣的秒數、並排、兩次。一個兩分鐘沒有人講話的圈子對這個產品來說是常態，所以這件事擋住了上線。

## 可觀測性與可靠度

- **串流的心跳是每 25 秒一行註解**，因為超過 130 秒的安靜會被前面的 proxy 切掉。它不帶任何成員讀得出來的時間
  資訊。
- **每個 API 行程對資料庫持有一條監聽連線**，並從它把事件散出去，所以不只一個行程可以服務同一個圈子。那條連線
  死掉的時候，這個行程會說出來：`/health` 回 503，帶著 `stream_listener` 和它從什麼時候開始掛掉，同時繼續服務
  讀取。在一次真的砍連線上量到：**0.18 秒內回 503，1.23 秒內在新連線上恢復。**
- **一個 API 行程不會去服務一個它不是照著寫的 schema。** 它在啟動時讀 migration 版本，如果資料庫落後、超前、
  或從來沒 migrate 過，就把兩個版本都寫進 log 然後結束 —— 所以部署會在錯的那個 container 上失敗，而不是在某個
  成員的請求裡面。
- **對模型的連線會重試，而且重試次數會印出來。** 這條路徑上一個冷的模型表現得像*掛掉*而不是慢：第一個請求失敗，
  十二秒後的重試半秒就回。一條不穩的連線讀起來是一個數字，而不是一個很慢的晚上。
- **一個失敗的排程任務會送一則訊息**，帶的是 log 在 container 裡的路徑，永遠不是一個 URL。全新 clone 預設是
  關掉通知的，而且有一個故意會失敗的任務存在，好讓這個通道本身可以被測試。

## 快速開始

```sh
cp .env.example .env                # names only — the comments state the shape of every value
docker compose run --rm migrate     # the schema, once per version
docker compose up -d --wait         # the stack
curl -s localhost:8080/health
#   {"status":"ok","database":"reachable","instance":"…","stream_listener":"up"}
```

**是兩個指令而不是一個**，因為 schema 那一步離開了整套 stack 的開機流程，好讓多個行程不會搶它。它是冪等的
—— 對一個已經是最新的資料庫跑，它什麼都不會做。

- **`localhost:8080`** —— 這個 app；API 和資料庫只在 compose 網路裡面連得到。Airflow 介面有自己的連接埠和
  自己的名字，寫在 `.env.example` 裡，連接埠就住在那裡。
- 氣象匯入需要一把免費的中央氣象署開放資料金鑰（opendata.cwa.gov.tw），在 init 時讀一次進 Fernet 加密的
  Airflow Connection —— 永遠不從環境變數讀、永遠不進 XCom 或被渲染的樣板欄位。另外五個開放資料檔案不需要任何
  憑證。新的排程任務會以**暫停**狀態出現（`airflow dags unpause <dag_id>`）。

手動跑一個匯入 —— `0` 有存或沒有變化、`1` 來源失敗、`2` 兩個版本訊號不一致 —— 或是把模型開起來做回填：

```sh
docker compose exec api python -m upto.ingest.run_places
docker compose exec api python -m upto.ingest.run_business_tax

docker compose --profile model up -d ollama
docker compose exec ollama ollama pull gemma2:2b
docker compose exec ollama ollama pull snowflake-arctic-embed2
docker compose exec api python -m upto.classify.run 63000010 --rag --embed arctic
#   exit 3 = model absent, nothing written
```

**血緣也服務給模型看。** 任何一筆讀數都可以追到它的發佈、它的內容雜湊值，以及寫下它的那次執行，走 stdio 上的
MCP：

```sh
docker compose exec -T api python -m upto.lineage.mcp_server
```

五個工具回答：`run_history`、`run_detail`、`publication_detail`、`forecast_reading_source`、
`observation_reading_source`。第六個 `explain_place_loss` 被列出來**只是為了拒絕** —— 那條路會走進成員私下的
選擇，而一個今天只是還沒有某個功能的工具，會在第一個覺得它有用的人出現時長出那個功能。有一個測試斷言這個拒絕。

## 測試

67 個測試檔案。抓取、雜湊和解析都有不需要網路也不需要資料庫的單元測試，那就是排程任務可以這麼薄的原因 ——
它們只提供*什麼時候*和*用哪個資料庫*：

```sh
python3 api/tests/test_cwa_ingest.py    # and test_fda_ingest, test_fia_ingest, test_dice_table,
python3 api/tests/test_weight_fold.py   # test_classify, test_web_surface, test_evaluate_draw …
```

整合測試自己建立、自己丟掉資料庫，在那個只給測試用、握有擁有者憑證的服務裡 —— 永遠不在 `api`，它連線用的角色
沒辦法 `create database`。每一個來源都被證明是冪等的，走它真正的命令列入口跑兩次，每一個欄位都比對：

```sh
docker compose run --rm tests python /srv/tests/test_place_ingest_integration.py
docker compose run --rm tests python /srv/tests/test_business_tax_integration.py
```

每一次 commit 都會通過 pre-commit hook 裡的六道本地檢查。其中五道只需要標準函式庫，所以一個 clone 不需要任何
工具鏈就能 commit：密鑰掃描、`app/` 邊界、對每一個成員讀得到的字串做字型子集檢查、伺服器自己的文案在出貨字型
裡畫得出來，以及風險登記簿的編號。第六道用 `ruff` 讀每一個 staged 的 Python 檔案，拒絕語法錯誤和真正的問題
—— 沒定義的名字、沒用到的 import、參數沒去處的 `.format` —— 而完全不管排版。

## 隱私

**作者身分在結束時就在資料庫裡死掉。** 結束一個回合會觸發一個 trigger，把那個回合的 `proposal.member_id` 設成
空值，就在讓結果落地的那個交易裡。用 trigger 而不是應用程式的程式碼，因為手動用 SQL 結束、一個修補腳本、或是
第二條程式路徑，都會各自把作者身分留下來，而且都不會報錯。

即時串流上不帶任何成員，而且不帶任何成員讀得出來的時間資訊：寫入一個偏好會回 204 而且不發出事件，因為五個人的
時候，一個事件發生的時刻離一個名字只差一次猜測。偏好預設只存在於這一餐，除非被留下來，每晚由一個角色只能讀和
刪那張表、其他什麼都不能做的工作抹除；超過九十天的氣象讀數也一樣，除非被某次擲骰釘住。

## 範圍

任何爬來的頁面。尺寸是給一個小團體的：房間狀態存在行程裡，五個朋友而不是五千個。這是一個作品集專案，在一個
私有 repository 裡開發，每次合併之後抽出到這裡，所以 commit 訊息帶著每一次改動背後的理由。
