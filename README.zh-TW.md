**一群人一起決定一餐。選的是一對加權的骰子。**

給一群永遠喬不定去哪吃的朋友。他們想看到一家店為什麼贏，一份排名說服不了他們。

**試用：[uptoyou.jacksong-tw.com](https://uptoyou.jacksong-tw.com)**

打開網站，開一個自己的圈子，把連結傳給朋友。想自己跑，見文末的快速開始。

## 這個專案在解決什麼問題？

### 1. 沒有人想當做決定的人

幾個朋友要吃晚餐。每個人都有一點偏好，可是沒有人想扛這個決定。結果要嘛聽最大聲的那個，要嘛花二十分鐘決定不了。

### 2. 排名只是把爭論搬家

軟體通常的答案是排名。排名只是把爭論搬到別處。大家改成爭這份排名對不對。從排名裡挑的那個人，還是得扛這個選擇。

### 3. 這是一套推薦系統，差別在最後一步

底下的骨架，跟任何推薦系統一樣：

| 步驟 | 在這裡是什麼 |
|---|---|
| **資料來源** | 七個政府來源，各有各的更新節奏，最後落在同一個資料庫 —— 難的不是接進來，是讓它們對得起來：用統編和登錄字號 join，完全不做模糊比對 |
| **特徵** | 擲骰的那一刻，每家店 × 這一輪：它的分類（生成的）、桌上有沒有人避開這個分類、那一區那個鐘點的降雨機率、上一次簽到去的是不是這家 |
| **打分** | 每個特徵回一個係數，係數相乘，乘出來的就是這家店的權重 |
| **選擇** | 權重變成 36 種結果的整數分配，再由一顆在任何人提店之前就鎖住的種子指到其中一格 |

**有兩件事，我們刻意不照廣告或電商推薦的做法。**

**打分是寫出來的，不是學出來的。** 要訓練一個打分模型，得有標準答案 —— 人們實際去了哪 —— 而這個產品沒有：目前每一個圈子裡的每個成員都是測試帳號。學在沒有答案的資料上，就驗證不了；一個驗證不了的模型，比一條講得出理由的規則更糟。所以那三個常數是政策：上次去過的那家 ×0.5、一個人避開的類型 1/N、下雨的時段 ×0.8。

**最後一步是抽，不是取最高分。** 推薦系統算完分數，回傳最好的幾個；這裡算完分數，然後抽。權重高的店占 36 格裡的格子多，比較容易中，但不保證中 —— 所以開獎顯示的是**被選機率，不是推薦分數**。「系統認為這家最好」和「在今晚的條件下，這家機會最大」，差別就在這裡。

## 為什麼用「加權骰子」？

骰子天生公平：沒有人挑，所以沒有人要替結果辯護。

但純粹的骰子會忽略這群人知道的每一件事，所以骰子要加權。兩顆骰子有 36 種結果，每家店分到其中幾格；在乎的事會改變它分到幾格。

有人避開的類型是**打折，不是否決**，而且折扣跟桌上的人數成比例：N 個人時，一個人反對，那家店少掉 1/N 的機率。5 個人時少五分之一，那家店還是抽得到。N = 1 時就等於否決 —— 一個人自己玩，那本來就是他自己的決定。

![The reveal — the winner, and every factor that moved its odds](docs/reveal-panel.png)

加權的骰子，要查得到才值得相信。每個因素在擲骰當下就存成一列，記著它從哪一筆資料算出來；開獎不會為了顯示再算一次，它讀的就是擲骰時用的那幾列。

**誰看得到什麼。** 成員看到贏家、骰子和一句話。完整的表（每個因素、它從哪來）是 operator 的畫面。差別在「請你相信」和「可以查」。偏好進來時私密，出去時看得見：移動機率的東西會顯示，誰要求的不顯示。

**而且隱私是在資料庫裡執行的。** 關閉一個回合會觸發一個 trigger，在讓結果落地的那個交易裡，把 `proposal.member_id` 設成空值。手動用 SQL 關閉、或一個修補腳本，都會把作者身分留下來，而且都不會報錯。寫入一個偏好會回 204 而且**完全不發出事件**，因為在一個小圈子裡，一個事件發生的時刻離一個名字只差一次猜測。偏好預設只存在於這一餐，每晚由一個只能讀和刪那一張表、其他什麼都不能做的角色抹除。

## Up to you 的解法

每個因素都乘上一家店在三十六種結果裡的那一份。這些數字存在資料庫裡，開獎時直接讀。

| 因素 | 對一家店的機率做什麼 | 為什麼 |
|---|---|---|
| 它那一區在下雨 | 降低。基準是今晚池子裡最乾的那一區 | 下雨天走過去是真的成本。這是今晚的事實，跟店本身無關 |
| 這個圈子上禮拜去過 | 砍一半 | 換換口味，但選項還在。只有簽過的行程算數，只被擲到、沒簽的店不受影響 |
| 有人避開它的類型 | 降低 1/N，N 是桌上的座位數 | 這是折扣。五個座位裡一票反對，和兩個座位裡一票反對，效果不同 |
| 什麼都沒發生 | 不動它 | 起點的權重是 1。沒有作用的因素會畫成一列空的，不會消失 |

## 專案特色

- **35,965 家店**，來自七個公開政府來源。每次抓取都以內容定址，沒變的檔案不花成本。
- **一個分類器，在凍結的 200 列集合上評分**。四個地端模型在上面比較：72.0 · 71.0 · 70.5 · 65.5。
- **每個因素都是一列存下來的資料**，連著它算出來的那一筆讀數。開獎讀回那幾列，不會為了顯示再算一次。

## 效能、優化結果

**這些數字沒有一個是調參數調出來的。** 每一行都是同一個問題問兩次：這件工作需不需要做，以及需不需要在這裡做。

| 項目 | 之前 | 之後 | 量在哪裡 |
|---|---|---|---|
| 沒有新檔案的那一天 | 15.0 秒 | **1.6 秒** | 執行紀錄，8 天，7 個來源 |
| 為範例集嵌入一個名字 | 0.481 秒 | **0.045 秒** | 100 個名字，量兩次，09-04 |
| 分類一個名字 | CPU 上 12–19 秒 | 8 GB 顯示卡上 **1.27 → 0.92 秒** | 一個行政區，1,318 列 |
| 名冊匯入的記憶體峰值 | 172 MB | **77 MB** | 一台 2 GB 機器，09-05 |
| 服務中的整套 stack 靜置 | 1,131 MiB | **1,009 MiB** | 一台 2 GB 機器，09-07 |
| 一次長時間的分類 | 頭尾差 1.7× 變慢 | **平的** | 36,014 列、10.5 小時，09-03 |

記憶體的數字是在當時那台 2 GB 機器上量的。那台機器後來換大了。[長版本](docs/decisions.md)有後面四項的推演過程。

## 系統架構

![Architecture — the stack as it is served](docs/diagrams/architecture.png)

*一台主機、一個 compose 檔，一個資料庫同時做關聯式和向量的工作，所以每個服務都放得進一台小雲端機器。Cloudflare 在邊緣終止 TLS，來源端用自己的憑證回應。四個 Airflow 服務和
API 共用同一個 PostgreSQL，各自用自己的角色連線。*

| 層 | 跑什麼 |
|---|---|
| **前端** | Vite + React 19 + Tailwind 4 + shadcn/ui，在 proxy image 裡 build。沒有 CDN，執行時不抓任何東西。兩套子集字型跟著 bundle 一起打包。 |
| **API** | Python、FastAPI、SQLAlchemy 2.0，全程 async。47 個手寫的 Alembic migration。 |
| **資料庫** | PostgreSQL 17。七個登入角色，一個邊界一個：API、匯入、血緣工具、每晚的抹除、備份、數值檢查、擁有者。擁有者只有那個一次性的 migration container 拿得到。 |
| **向量** | pgvector，在同一個資料庫裡。 |
| **排程** | Apache Airflow 3、LocalExecutor，在同一套 compose 裡。它的中繼資料是同一個 PostgreSQL 裡的第二個資料庫。 |
| **模型** | Ollama 跑在家裡那台機器的 8 GB 顯示卡上，由開發機分批使用；正式主機不跑模型。`gemma2:2b` 生成，`snowflake-arctic-embed2` 檢索。 |

### 資料規模

正式機的資料庫佔 **224 MB**。裡面有 35,965 家店（其中 25,031 家有分類），以及它載入的那一版參考名單的 36,376 列。

### ETL 流程

![The ETL pipeline — seven sources into one ledgered store](docs/diagrams/etl-flow.png)

**一次抓下來的檔案，身分是它位元組的雜湊值，不是時間戳記** —— 這叫內容定址，git 給 commit 取名字用的也是同一招。時間戳記會在資料沒動時改變，也會在資料變了時不動。參考名單的匯入先對一個 17 MB 的 zip 取雜湊，再用 `insert … on conflict do nothing returning id` 去搶這筆發佈：拿到 id，才去解壓縮裡面那個 99 MB 的 CSV；沒拿到，這次就到此為止。

**這不是 upsert。** upsert 兩種情況都會寫，而且要先解析完檔案才知道要寫什麼。這裡「撞到」本身就是答案：內容沒變，整個解析可以省掉 —— 沒有變化的一天 1.6 秒，真的要存 15.0 秒。而且搶那一列是單一一個敘述，兩個同時開始的執行不可能都判定檔案是新的；先 `select` 再寫就會兩個都放行。

每一次嘗試都寫一列執行紀錄，所以「沒有變化」和「失敗」是兩個被記下來的結果，不是兩種沒有紀錄。只靠「沒有紀錄」去推論，一個壞掉的來源會健康地躺一個禮拜。

## 關鍵技術決策

### 1. 店名：清洗、解析，真正的難點

**難點** 政府的餐飲名單寫的是「安心食品服務股份有限公司」。你認得的是「摩斯漢堡」。同一家公司，兩個名字，只有一個人看得懂。

![The name ladder — sign, then brand, then registered name](docs/diagrams/name-ladder.png)

**做法** 顯示名稱分三層找：先找稽查員記下的招牌，再找品牌，最後才用登記名稱。三個來源用登記號 join，優先順序固定，完全不做模糊比對。否決掉的是只用登記名稱，還有跨來源做字串相似度。

**結果** 登記名稱裡有 40.2% 是法人字串，根本沒有指涉任何一家店。有招牌的那些列裡，招牌和登記名稱有 93% 不一樣。品牌表把它涵蓋到的公司改掉了 57%。試用過 Overture Maps 這個開放的全球地點資料集，放棄了：可信的配對只有 39.5%，只靠地址 join 有 46% 是錯的。店名階梯碰得到多少，量在目前這一版參考名單的 36,376 列上：

| 階 | 列數 | 佔比 | 其中仍然是公司名的 |
|---|---|---|---|
| 招牌（店面層級） | 1,363 | 3.7% | 3.2% |
| 品牌（只限單一品牌公司） | 4,003 | 11.0% | 44.2% |
| 登記名稱（剩下的） | 31,010 | 85.2% | 32.9% |

這道階梯碰到全市的 14.8%。全部列裡有 33.1%，顯示出來的字串仍然是公司名。有招牌的地方，名字就是對的。

### 2. 分類：RAG

**難點** 沒有任何公開來源說一家店賣什麼。沒有一個官方欄位寫著「這是一家麵店」。所以分類是生成出來的：地端的模型讀這個專案能找到的最佳店名，從十三個分類裡選一個，正確率量在一個凍結的集合上。

**做法** 分三步：

- **Retrieval（檢索）**：用 pgvector 找出五個名字最像、已經標記好的店家。
- **Augmented（增強）**：把這五個連同要分類的名字一起放進提示，當作示範題。
- **Generation（生成）**：模型從十三個分類裡回答一個。

標註過的範例名字嵌入 pgvector，就是這裡說的範例集。缺少的知識用資料補，提示詞和權重都不動。否決掉的是再改一版提示詞，還有微調。

**為什麼模型跑在地端。** 排程跑的是 `gemma2:2b` 負責回答、`snowflake-arctic-embed2` 負責找鄰居，兩個都跟資料庫同一台，只做批次，沒有回填時就關著。**不接雲端 API 的理由有三個，而且是三種不同的成本。**

- **額度**：`gemini-3.5-flash-lite` 的免費層一天 500 次呼叫，3,300 家店要跑七天；同樣的工作地端一個晚上做完。
- **資料**：店名不會離開存著它的那台機器。
- **時效**：分類是半夜的批次，沒有人在等它回來，所以快一秒買不到任何東西。

它留下來當基準線：在第一版凍結集合上量到 60.5%，跟上面那張表不能直接比 —— 集合換過，中間有十九列重新標註過。

**結果**

![The evaluation loop — how a classifier candidate is scored](docs/diagrams/evaluation-flow.png)

*同樣 200 列凍結的資料，每個模型跑一輪，評完分就不再重跑。*

改提示詞那一版在固定集合上*掉*分（51.5 → 49.5）。同一個集合上加檢索，`gemma2:2b` 從 51.5 → 61.0，`llama3.2:3b` 從 37.0 → 58.0。`qwen2.5:3b` 卻是 51.0 → 48.5。同一個範例集，對其中一個模型是雜訊。所以模型和範例集的配對是量出來的。

*目前的表*：提示詞 v7、十三個分類、`testset_v3`。範例集同一個（`snowflake-arctic-embed2`、五個鄰居）。每一輪都在家裡那台機器上跑，走排程任務用的同一個中繼：

| 模型 | 授權 | 匯總正確率（200 列） |
|---|---|---|
| `qwen2.5:7b-instruct` | Apache-2.0 | **72.0%** |
| `gemma2:2b` | Gemma terms | 71.0% |
| `llama3.2:3b` | Llama 3.2 community | 70.5% |
| `qwen2.5:3b-instruct` | 研究授權，只能評測 | 65.5% |

三個模型彼此差不到兩分。其中一個每列的成本是三倍。排程任務留下 `gemma2:2b`。託管的比較基準只在第一個集合上量過，60.5%。

*嵌入模型用同樣的方法篩過* —— kNN-1，`testset_v3`，留一法：直接拿最近那個鄰居的分類當答案。

| 嵌入模型 | kNN-1 正確率 |
|---|---|
| `snowflake-arctic-embed2`，不加前綴 | **55.0%** |
| `snowflake-arctic-embed2`，加它自己的 `query:` 前綴 | 53.5% |
| `e5`，加 `query:` | 51.5% |
| `0.6b`，加指令 | 51.5% |

沒有一個贏過原本在用的那個，而且它**不加前綴**最好：那張卡自己的前綴要花掉 1.5 分。`qwen3-embedding:4b` 根本篩不了 —— 它輸出 2560 維，欄位是 `vector(1024)`，沒有為一個還沒贏過任何東西的候選去放寬欄位。鄰居要取幾個也在同一個集合上篩過，定在五個。

### 3. 官方行業代碼能決定什麼

**難點** 稅籍登記有行業代號。它只決定它能決定的，大約十列裡只有一列。

**做法** 稅籍代號在明確的時候說了算，其他交給模型。否決掉的是用代號當分類器，還有完全不理代號。

**結果** 代號可以定全市 10.9% 的列。一家咖啡連鎖的 245 家分店登記在批發代號底下，只看代號會把每一家都標錯。join 本身是安全的：去掉法人形式的字尾之後，名稱一致率 99.78%。地址就不安全，89.8% 不一樣。[長版本](docs/decisions.md)把同一個問題拿到那 200 列評分資料上量，站得住腳的上升空間是 +4 列。

### 4. 資料匯入：內容定址與執行紀錄

**難點** 每個來源自己決定什麼時候更新。沒有變化的日子，也要分得出「沒變」和「壞了」。

**做法** 每個抓下來的檔案一列發佈，每一筆記錄一列資料。另外一本執行紀錄，沒有變化的那一天寫一次心跳。否決掉的是就地覆寫，還有用猜的排程去配合每個檔案的更新頻率。

**結果** 每個來源在位元組相同時重跑，結果都一樣。每一張表的每一個欄位都比對過，走真正的命令列入口跑兩次。在參考來源上，沒有變化的路徑花 1.6 秒，真的要存花 15.0 秒。各來源：沒有變化的一天 0.31–3.58 秒，真的要存 0.31–25.03 秒。

*量在排程本身上*：8 天、332 列執行紀錄，對上 361 個 Airflow task instance。沒有加任何量測工具，沒有加任何欄位：

| 來源 | 有存 p50 | 沒變化 p50 | 執行紀錄列數 |
|---|---|---|---|
| 中央氣象署 鄉鎮預報 | 2.99 秒 | 1.85 秒 | 149 |
| 中央氣象署 測站觀測 | 3.09 秒 | 0.31 秒（n=1） | 149 |
| 食藥署 餐飲場所 | 還沒有 | 1.88 秒 | 5 |
| 食材登錄 品牌 | 0.57 秒 | 0.96 秒 | 8 |
| 衛生評核 招牌 | 0.31 秒 | 0.43 秒 | 7 |
| 商業登記 狀態 | 25.03 秒 | 2.09 秒 | 7 |
| 營業稅籍 | 12.95 秒 | 3.58 秒 | 7 |

**在最大的來源上，沒有變化的一天比有存便宜 3.6×**，在名冊上是 12×。這就是「先搶再解析」這條捷徑省下的成本。**排程本身每個任務固定花 1.2 秒**，來源花半秒或二十五秒都一樣。**排程器不是瓶頸：**全部 361 個任務的佇列延遲 p50 是 0.05 秒，最差 4.2 秒。這些數字回答不了抓取、解析、儲存各花多少，因為沒有任何東西記錄它。

### 5. 觀測性

**一個跑著的產品要說得出兩句話：「我還在」和「我還聽得到資料庫」。** 兩句都是在回答同一種壞法 —— 有東西安靜地不動了，而且沒有人說。

- **「我還在」是每 25 秒一行註解。** 前面的 proxy 會把安靜超過 130 秒的串流切掉，而被切掉的串流之後什麼都送不到，看起來卻跟「今晚沒事發生」一模一樣。心跳的作用就是讓那段安靜不再有兩種解釋。
- **「我還聽得到資料庫」是 `/health` 回答的。** 每個 API 行程握著一條監聽連線，事件從那裡散出去，所以不只一個行程可以服務同一個圈子。那條連線死掉時，行程會自己說出來：回 503，帶著掛掉的時間，讀取照常服務。在一次真的砍連線上量到：**0.18 秒內回 503，1.23 秒內在新連線上恢復。**

### 6. 可靠性

**這裡講的可靠性不是「不會壞」，是壞的時候錯誤出現在對的地方。三種壞法，三個位置：**

- **部署錯了 → 錯誤停在部署，不會走到成員面前。** API 行程啟動時先讀 migration 版本；資料庫落後、超前、或從來沒 migrate 過，它把兩個版本寫進 log 然後結束。壞掉的是那個 container，不是誰的請求。
- **依賴變慢 → 記成一個數字，不是一個很慢的晚上。** 模型平常不佔著顯示卡的記憶體，所以每天第一個請求要等它載入十幾秒 —— 而從呼叫端看，「正在載入」和「機器掛了」長得一模一樣。所以重試次數會印出來：第一個請求失敗、十二秒後重試、半秒就回，這三個數字說得出那是冷啟動，不是整晚不穩。
- **告警通道自己壞了 → 用一個故意會失敗的任務去測它。** 排程任務失敗會送一則訊息，帶 log 在 container 裡的路徑，永遠沒有 URL（全新 clone 預設關掉通知）。「沒有告警」和「告警壞了」從外面看一樣，光是等分不出來。

冪等性在第 4 節；測試的數量在下面的「其他六個決定」。

### 其他六個決定

- **向量搜尋是 Postgres 的擴充，不另外開服務。** 範例集是三個嵌入模型合計 537 列。為這些列多養一個有狀態的服務，還要備份、要監控，不值得。
- **評測集合是凍結的、分層的，標註者是誰有寫出來。** 它抓到一版提示詞，讀起來更好，分數卻更差。固定集合存在的唯一理由就是這個。
- **子字串搜尋維持循序掃描。** trigram 索引（把每個字串切成三個字元一段，再對那些片段建索引）在 31 個實際查詢裡改變了 0 個執行計畫。真正的成本是一個對每一列候選再跑一次的子查詢，每按一鍵執行 35,533 次。
- **那台小機器扛不住自己的夜間工作。** 一次匯入跑起來時，可用記憶體只剩 49 MB；調整之後最差的時刻是 398 MB。整套 stack 靜置從 1,131 → 1,009 MiB。
- **雲端負責服務，家裡那台負責算。** 一張 8 GB 的顯示卡處理帶檢索的批次，一個名字 0.92 秒。同一台機器的 CPU 要 12–19 秒。
- **每晚的備份做過還原演練，不是假設。** 19.7 MB 在 3.7 秒內 dump 完，9.4 秒內還原進一個全新的資料庫，筆數相同。

**測試是 74 個測試檔案、兩種節奏**，而且每一次 commit 都要過六道本地檢查。host-side 不需要網路也不需要資料庫；build-and-drop 自己建資料庫，跑在唯一握有擁有者憑證的那個服務裡。六道檢查裡有五道只需要標準函式庫，所以一個 clone 不需要任何工具鏈就能 commit。

[長版本](docs/decisions.md)有這六個的完整內容。另外寫了每個來源存什麼、十三個分類、清單外的答案怎麼被拒絕。凍結的評測集合怎麼抽出來，也在那裡。

## 怎麼做出來的

**讓七個 session 能運作的不是分工，是沒有人檢查自己的工作。** 一位開發者指揮七個 Claude Code session，每個 session 只有一份工作。背後的工具（commit 前的檢查、專案的 skill、規劃文件）放在私有的開發 repository，不在這份公開版本裡。

| Session | 唯一的工作 | 可以改哪些檔案 |
|---|---|---|
| 協調 | 把每個待決的問題整理成一個建議、它的代價和不選的做法，交給開發者決定；保管決定與計畫 | 規劃文件 |
| 後端 | API、資料庫、Airflow、工具 | `api/`、`airflow/`、`db/`、`compose.yaml`、`evaluation/` |
| 前端 | 畫面與 proxy | `web/`、`proxy/` |
| 讀程式 | 每個後端改動上線前都讀一遍，看不到寫的人怎麼想 | 自己的報告 |
| 測頁面 | 改動上線前，用各種訪客的身分量實際服務的畫面與 API | 自己的報告 |
| GPU 主機 | 在家裡的顯卡上跑模型和長時間的批次 | 自己的機器 |
| 研究 | 從有日期的來源讀別人怎麼解決同一個問題 | 自己的筆記 |

- **問題只透過一個 session 送到開發者面前，** 格式永遠一樣：建議、代價、不選的做法。
- **後端改動讀兩次。** 後端改動要有讀程式的報告和測頁面的量測才上線；畫面改動要有測頁面的量測。讀程式的 session 找到一個競爭條件（race condition）：十個座位的圈子會被擠進第十一個人；修法是鎖住那一列，`api/tests/test_self_serve_integration.py` 用兩條獨立連線同時加入來證明。
- **檔案歸屬。** 每個 session 只 commit 自己負責的路徑，而且逐一列出。
- **commit 前的檢查。** 每次 commit 前跑六項檢查，包括機密掃描、lint，以及檢查畫面上的每個字都在網站實際載入的字型裡。
- **專案 skill** 記下只需要學一次的事：在 GPU 主機上跑一輪評測，以及每個畫面的設計評分表。

## 限制與未來方向

**只有臺北**：十二個行政區、一個城市的開放資料；地址在匯入的邊界就正規化，因為同一份政府檔案把市名寫成兩種寫法。

**每一個來源都在它的授權範圍內使用。** 授權是非商業或不確定的來源就完全不用，整條管線裡沒有任何評分、任何評論、任何爬來的頁面。

**尺寸是給一個小團體的**，房間狀態存在行程裡。這是一個作品集專案，在一個私有 repository 裡開發，每次合併之後抽出到這裡，所以 commit 訊息帶著每一次改動背後的理由。

- **「有沒有真的去」是一筆交易，不是自我回報。** 到店的正解是會員掃碼或結帳紀錄，台灣這幾類供應商都是現成的
  —— 餐飲 CRM 與會員（Ocard）、餐飲 POS（iCHEF）、訂位與候位（inline）。**這裡一個都沒有用，也沒有接洽過**；
  這一行記的是這條路被看過，不是被走過。擋在前面的有兩件事，而且只有一件是技術問題：這種資料要靠商業合約才會流動，
  而個資法的目的外利用才是真正的問題 —— 夥伴當初蒐集那些紀錄，是為了經營它自己的生意，不是為了讓第三方拿去養一個吃飯的 app。
  在那之前，產品改成問桌上的人，便宜但也比較弱。
- **素食 從分類改成一家店帶著的屬性**（素食麵館 = 麵食 + 有素）。「我不能在這裡吃」是桌上的一個需求，折扣處理不了。分類集合回到十二個。
- **不只一個行程，前面放負載平衡器。** 事件匯流排已經在資料庫裡，schema 那一步也已經是部署的一步。
- **用 MLflow 管評測回合**，取代回合檔案自己手寫的記帳。
- **超市 分類與提示詞 v8。** 測試集必須先重抽，否則新的分數跟現在這個不能比。
- **文字轉語音與語音轉文字的評測回合**，給一支介紹影片用。評分方式跟分類器一樣：固定集合、先查授權、每個候選一個數字。

## 快速開始

```sh
cp .env.example .env                # names only — the comments state the shape of every value
docker compose run --rm migrate     # the schema, once per version
docker compose up -d --wait         # the stack
curl -s localhost:8080/health
#   {"status":"ok","database":"reachable","instance":"…","stream_listener":"up"}
```

**兩個指令。** schema 那一步離開了整套 stack 的開機流程，好讓多個行程不會搶它。migrate 可以重複跑：對一個已經是最新的資料庫跑，它什麼都不會做。

**全新 clone 開起來是空的，然後它自己會長出來。** 第一次參考名單匯入跑完之前沒有任何店家：排程在半夜抓，或是[手動跑](docs/operations.md)。**而店家要等分類回填跑完才會有分類**，那一步需要一台有顯示卡的機器。那是 clone 唯一不會自己抓的東西：沒有顯示卡就會有全部的店家、沒有分類，那是一個可以用的產品，只是有一欄是空的。

`localhost:8080` 是這個 app；API 和資料庫只在 compose 網路裡面連得到。氣象匯入需要一把免費的中央氣象署開放資料金鑰（opendata.cwa.gov.tw），在 init 時讀一次進 Fernet 加密的 Airflow Connection，另外五個開放資料檔案不需要任何憑證。新的排程任務會以**暫停**狀態出現。

手動跑匯入、跑分類回填、跑測試、用血緣工具：[docs/operations.md](docs/operations.md)。
